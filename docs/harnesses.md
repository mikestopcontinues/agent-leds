# Harnesses

What each agent harness reports to the service and where it falls short. [design.md](design.md) covers what the service does with the reports.

The service reads every harness's own files as they change. Claude Code's and Junie's files say all it needs, and Grok's all but a wait for a tool's approval (listed under its gaps), so it registers no hooks with them. With Codex and Cursor, `agent-leds install` registers `agent-leds hook <harness>` for the one or two events listed below that their files do not record; OpenCode and Pi load a plugin of ours that runs it for what their files leave out. The hook passes the event to the daemon with the processes it runs under, prints nothing and always succeeds. So it never holds up a turn and never answers a permission request. Where a harness takes a hook's silence for an answer, that event is not hooked. Whatever the hooks say, a session leaves when the process its harness names ends; each section says how that process is known. No timer guesses what a session is doing and the process table is never listed, so a moment that neither a file nor a hook records is a gap, listed under its harness. An interrupt leaves the session tracked with no light, idle until its next prompt.

[coverage.md](coverage.md) lists every signal each harness gives, how each is known, and the moves each cannot make. `agent-leds doctor` reads each harness's files with the same readers and says how many sessions they show running, or what keeps it from reading them.

## Claude Code

Each running Claude Code process, in a terminal, the desktop app or a background session `claude --bg` started, keeps a file in `~/.claude/sessions/` with its session and whether it is busy, idle or waiting on the user, and each session writes its transcript to `~/.claude/projects/`. The daemon reads both as they change. Claude Code keeps that folder at `$CLAUDE_CONFIG_DIR` when it is set, and the daemon finds it the same way, from the environment launchd starts it with, which a `CLAUDE_CONFIG_DIR` exported in a shell's profile never reaches: set it there too with `launchctl setenv CLAUDE_CONFIG_DIR <folder>`, then run `agent-leds install` to restart the service. `agent-leds doctor` reads the folder the service reads and says when the shell's `CLAUDE_CONFIG_DIR` names another; it has a Claude Code line once the folder exists where the service or the shell finds it, as `agent-leds install` counts Claude Code in use.

| What Claude Code writes | Session becomes |
| --- | --- |
| A prompt in the transcript | working |
| The session file waiting on a permission | question |
| The session file waiting for input needed | question |
| The desktop app's log opening a dialog for the session, as computer use's and the in-app browser's approvals do, which leave the session file busy | question |
| The wait over in the session file and the log both, while the turn runs | working |
| The session file done waiting on a request made after the turn ended, such as a worker or sandbox request | back to the light the wait covered, unannounced |
| The end of a turn whose last line ends in a question mark, or, in the desktop app, whose last `wrap_up` call put a question in the next-step box | question, as a weak signal |
| The end of a turn while the session file stays busy | working, in the background |
| The end of a turn otherwise, or a background turn going idle | stopped |
| An API error in the transcript | error |
| An interrupt in the transcript | idle (no light) |
| The session file gone or naming another session, or its process gone, while no other process runs the session | removed |

The desktop app raises some dialogs itself, and the session file goes on saying busy while they wait: computer use's request for access to an app, and the in-app browser's approval of a site or an action. The app logs every dialog it shows a session to `~/Library/Logs/Claude/main.log`, its own and those Claude Code relays to it, such as a Bash permission or `AskUserQuestion`: `Emitted tool permission request <id> for <tool> in session local_<id>` as it opens, and `Received permission response for <id>: …` or `Permission request <id> for <tool> aborted` as it closes. The app's file for its session, `~/Library/Application Support/Claude/claude-code-sessions/<account>/<organization>/local_<id>.json`, names the Claude Code session in `cliSessionId`. The daemon reads the log as it grows, and when the app rotates it at about 10 MB, renaming it to `main1.log` and starting a new one, reads the rest of the old file there before the new one from its start, so no line is lost or read twice. A wait the session file and the log both tell is one wait: the session waits while either holds it, on the session file's wait when it has one, and is answered only once neither does, so it shows one question and the end of one never lets go of a wait the other still holds. A dialog holds up only the run of the session that raised it: one opened before the process now running the session started, by the log's local time, is left by a run that was killed or quit while it was open, and holds up no later one. A daemon that starts reads the log back to the app's last start, which it records as `Starting app`, through as many of `main1.log` to `main4.log` as that takes, and a dialog opened since and not closed holds its session as a question, if the run that raised it runs; a dialog of an earlier launch is not open, and the app starting again closes every one. The log is the app's own and undocumented; the fixtures in `tests/fixtures/claude/` hold its lines as written. All 138 dialogs in six weeks of the author's log (69 for `AskUserQuestion`, 36 relayed permissions, 21 of the in-app browser and 12 of computer use) were closed by a later line. The password manager's approval for `request_credentials` and the card `start_session` offers are not logged as dialogs, so the session shows working while they wait.

A turn that ends with a subagent or a workflow running in the background is not the session's last word: Claude Code keeps the session file busy until that work is done, so the session stays green until it goes idle, and then it shows as stopped. A Stop hook that blocks the end of a turn shows the turn working again once Claude Code records what the hook told the model, so the session shows as stopped only while the hook runs; one that fails without blocking ends the turn as usual. A dialog changes no light. Claude Code writes that one is open in place of busy or idle, mid-turn too, and not whether it holds anything up, so `/model` or `/config` opened at the prompt or during a turn holds nothing up, and a dialog that does want an answer, such as auto mode asking whether to stay on, shows as the light it opened over. While a dialog is open the file does not say whether work a turn left runs on: a turn that ends then shows as stopped even if that work runs, and so does such a session when the daemon starts. The files do not say whether a wait began before the turn's end or after it, so a daemon that starts during one takes a worker or sandbox request, which Claude Code makes outside a turn, to have begun after the end, and any other wait to have held the end up. The files are undocumented; the fixtures in `tests/fixtures/claude/`, recorded from real sessions, pin what the daemon expects of them. A run nobody watches is not shown: one of `claude -p` or of a program on the Agent SDK, whose session file names its entrypoint `sdk-cli`, `sdk-ts` or `sdk-py`.

## Codex

A Codex process holds a lock on `~/.codex/thread-writer-locks/<thread>.lock` for each thread it runs, and appends the thread's rollout, `~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<thread>.jsonl`, a record at a time. The daemon follows a thread while its lock is held: the lock deleted is a quit, and a lock left unlocked is a process that was killed. The date folders are listed, never computed, since a resumed thread goes on writing to the rollout in the folder of the day it began. Compressed rollouts and `~/.codex/archived_sessions` are never appended to, and are not read.

| What Codex writes | Session becomes |
| --- | --- |
| `task_started` | working |
| A `request_user_input` call with no output yet | question |
| The question's output | working |
| `task_complete` whose last line ends in a question mark, or that holds a `<proposed_plan>` | question, as a weak signal |
| `task_complete` while an item of a `request_user_input_async` call has no answer since the last prompt the user typed | question, as a weak signal |
| `task_complete`, or a later change to `goals_1.sqlite`, with the thread's goal `blocked`, `usage_limited` or `budget_limited` and its `updated_at_ms` no earlier than the turn's `started_at` second | question, as a weak signal |
| `task_complete` while a subagent the turn started, or gave a `followup_task`, is still at work, or while the thread's goal is `active` with no continuation deferral | working, in the background |
| `task_complete` without an error while `queue_1.sqlite` holds a prompt the user queued for the thread | working: Codex starts that prompt next |
| `task_complete` otherwise, or, after the turn ended, the last such subagent completed or the goal stopped being active | stopped |
| `task_complete` with an error | error |
| `turn_aborted`, which a cancelled approval writes too | idle (no light) |
| The lock deleted or left unlocked | removed |

A goal is Codex's own loop: while the thread's row in `~/.codex/goals_1.sqlite` is `active` and `thread_goal_continuation_deferrals` has no row for it, Codex starts the goal's next turn itself (trigger `goal`), often within milliseconds of the last one's end. The rollout only ever writes `thread_goal_updated` as active, so the database is the record of a goal that went blocked or hit a limit. Codex leaves that status in place while the user goes on in the thread with typed, heartbeat and `send_message` turns, none of which touch the row, so a waiting goal asks only at the end of the turn it went waiting in: its `updated_at_ms` is no earlier than the second `task_complete`'s `started_at` names. The daemon reads the goal at each `task_complete`, and again when `goals_1.sqlite` or its write-ahead log changes while a turn's end is the last thing the thread did; it reads the queue at `task_complete` only, since Codex deletes the queued item as it starts that prompt's turn. Both are opened read-only for each read and closed again, which takes no lock Codex waits on and sees what Codex committed to the write-ahead log and has not checkpointed; a database no process has open has no log, and is read from its file as immutable. The daemon watches `~/.codex` for the databases, the locks and the rollouts together.

Nothing is written while an approval waits, so `agent-leds install` registers the hook for `PermissionRequest` alone, and removes the others an earlier version registered with their trust records. The hook makes the session a question only while its rollout has that turn open; the next tool output, completed item or `task_complete` in the rollout answers it. A daemon that starts inside a turn takes the same record to answer an approval the hook told before it started. Codex runs a hook only once its hash is recorded under `[hooks.state]`, so the install asks `codex app-server` for the hash and records it, which needs `codex` on the `PATH`. Codex keys that record by the hook's place among the groups of its event and the handlers of its group, so a hook of ours keeps its place, beside any handlers another tool added to its group, and if another tool reorders them, run `agent-leds install` again.

A thread whose `session_meta` names a subagent, by its `source` or its `thread_source`, is never followed: its parent's rollout says when it starts and completes, and the copy of the parent's history a forked subagent's rollout opens with is never read. That leaves out the agent that consolidates Codex's memories too. A thread the desktop app opened for an agent (`thread_source` `agent_created_thread`) is followed like the user's own. When the daemon starts, and when it first sees a thread's lock, it reads the thread's rollout back to the `task_started` of the last turn the user typed a prompt for (trigger `composer`, `queue` or `remote_android`), which leaves no async question from before it open, at most 16 MiB, and only what was written since the lock was taken, so a resumed thread does not replay its history and a prompt written before the lock is seen still counts. The files are undocumented; the fixtures in `tests/fixtures/codex/`, recorded from Codex 0.153.2 and the desktop app's 0.162 rollouts and databases, pin what the daemon expects of them. The gaps:

- A thread opened in the terminal shows only once its first prompt creates its rollout.
- An approval answered while the daemon was down still shows as a question when it starts, until the turn writes its next record, since nothing is written while an approval waits.
- An approval a subagent asks for is not seen: it is not known whether its hook names the subagent's thread or its parent's, and the subagent's thread is not followed.
- `request_user_input_async`, the desktop app's question, does not stop the agent, so the session stays working while it waits for the answer, and shows the question only once the turn ends. A prompt the user types lets every question before it go, answered or not, and a turn Codex starts by itself does not: while a question is open and a goal goes on by itself, each of the goal's turns ends on the question again. A question asked before the lock was taken, or further back than the 16 MiB a start reads, is not known.
- A goal's next turn can come long after the last one ended: of 1,086 goal turns that followed a goal turn in the desktop rollouts, 568 started more than a minute later, and the session shows working in the background meanwhile.
- A waiting goal made active again, or cleared, after its turn ended keeps the question until the next turn, since no move leaves a question for the background.
- A queued prompt the user removes just as the turn ends leaves the session working until its next turn. Whether Codex starts a queued prompt after a failed turn was not seen, so the failure shows.
- A failing request that Codex retries leaves no record, so the session stays working until the turn ends. After a turn ends on a capacity error (503), the desktop app can start it again by itself, as a turn with trigger `capacity_retry_automatic` (12 such turns in the desktop rollouts, 4 of them within a minute of an error), which shows working again after the error.
- A subagent that never reports completing keeps its parent in the background until the next prompt.
- A subagent started or given its task in an earlier turn does not keep its parent in the background: when the turn ends the session shows stopped while the subagent works. A `send_message` to a subagent starts no turn of its own, so it does not count either.
- A plan proposal is recognised by its `<proposed_plan>` block, which no rollout has shown yet.
- The engine the desktop app bundles, `codex app-server` 0.163, takes a thread's lock at `thread/start` and deletes it on SIGTERM, and unsubscribing from the thread did not release the lock within 60 s; Homebrew's 0.153 leaves the lock behind, unlocked, as a killed process does. That was seen with the engine alone, in a throwaway `CODEX_HOME`. The app itself, its durable host, and whether a thread the app unloads (after 3 hours idle, or past 10 inactive threads) lets its lock go were not observed, so a light could stay or vanish when the app unloads a thread.

## Grok

`~/.grok/active_sessions.json` lists each running Grok session with its process's pid and the microsecond that process started. Each session keeps a folder, `~/.grok/sessions/<cwd folder>/<session>/`, with two logs and a state file: `events.jsonl` says when a turn starts, waits and ends, `updates.jsonl` holds what the agent wrote and the subagents it started, and `plan_mode.json`, replaced whole at each change, says whether a plan waits on the user's approval. The daemon reads them all as they change. The events decide turns and questions, `plan_mode.json` decides a plan's approval, and the updates' `subagent_finished` decides the end of work left running after a turn; the updates are also read to their end when a turn ends, for its last message and the subagents still running. A daemon that starts reads the updates back to the last prompt. No hook is registered, and an install removes the `~/.grok/hooks/agent-leds.json` an older version wrote.

| What Grok writes | Session becomes |
| --- | --- |
| A row in `active_sessions.json` whose process runs | tracked |
| `turn_started` in the events, typed, sent now, or after a background subagent or command finishes | working |
| `tool_started` for `ask_user_question` | question |
| `awaiting_plan_approval` true in `plan_mode.json` during a turn, as `exit_plan_mode` shows its plan card | question |
| `tool_completed` for `ask_user_question`, or `awaiting_plan_approval` false again during the turn | working |
| `turn_ended` completed, whose last message's last line ends in a question mark | question, as a weak signal |
| `turn_ended` while the updates hold a subagent spawned and not finished | working, in the background |
| `turn_ended` with outcome `error`, as an API error ends the turn | error |
| `turn_ended` otherwise, including a cancel Grok made itself such as `max_turns` | stopped |
| `turn_ended` cancelled by Ctrl-C, the stop button, the dashboard or send-now, or by rejecting or cancelling a permission | idle (no light) |
| The row gone from `active_sessions.json`, as `/quit` leaves it even mid-turn, or its process gone | removed |

A row left by a process that was killed stays in the registry until another session starts, so a row counts only while its pid runs with the start it records. A subagent runs in a session folder of its own, beside its parent's, under an id the registry never lists, so it is never followed; the parent shows its work. A background command that finishes wakes the session with a turn of its own; one killed during the turn tells nothing more. A `!` shell command writes no turn to the events, so it shows nothing; the updates record it as a user message with the command in its `_meta`, which is not taken for a prompt. The files are undocumented; the fixtures in `tests/fixtures/grok/`, recorded from Grok 1.0.77, pin what the daemon expects of them, and `agent-leds doctor` says when `grok --version` or the newest session's `schema_version` differs from what they pin, since Grok updates itself by default.

Grok also runs the hooks in `~/.claude/settings.json`, unless `~/.grok/config.toml` sets `[compat.claude] hooks = false`, so a Claude Code hook fires inside every Grok session with Grok's session id. Doctor reports the Claude Code hooks an older agent-leds left there on the Grok line too, and any hook written for Claude Code must expect Grok's ids. The gaps:

- A wait for a tool's approval shows as working. Every tool, read-only ones too, writes a permission request and then its answer, and a request Grok approves by itself looks the same as one that waits on the user until the answer comes: the answer comes within 7 ms, or after the user has decided. Telling them apart by how long the answer takes would be a guess. `enter_plan_mode` was approved by itself even in the default permission mode.
- A plan approval counts only while its turn is open. A message typed at the plan card answers it, and the agent may show the plan again, which blocks again. Ctrl-C did nothing at the card, so what a cancel there leaves in `plan_mode.json` is unknown.
- No diff review card was seen: in the default permission mode, after a plan was approved, file writes were approved by themselves.
- A turn that fails is known from its `turn_ended`, written before Grok runs its `StopFailure` hooks. That was seen for a 400; whether a refusal or a `max_output_tokens` end writes outcome `error` is unverified. A request that cannot connect retries without end and never ends the turn, so the session stays green.
- A run with `grok -p` gets no row, so it is not shown.
- A background command left running ends its turn as stopped, as a subagent left running does not. Only its `task_completed` says whether it wakes the session, so nothing at its start tells a dev server, which never exits, from a `sleep`; one that finishes wakes the session with a turn of its own, which shows working and then stops again.
- Work that finishes after its parent's turn without waking it should show the session as stopped. That was never seen: subagents and commands that finished after their turn woke the parent, and the ones that did not wake it finished inside the turn.
- The leader process (`use_leader`) and several windows on one session have not been tried.

## Cursor

The daemon reads three things Cursor's CLI writes. Each chat's transcript, `~/.cursor/projects/<slug>/agent-transcripts/<chat>/<chat>.jsonl`, is written at the checkpoints of a turn. Each chat's store, `~/.cursor/chats/<hash of the cwd>/<chat>/store.db`, is a SQLite database the process holds open, from the chat's first prompt, while the chat is the one it is on; `/new`, or resuming another chat, lets go of it, which deletes its write-ahead log, `store.db-wal`, at once. Each running process marks itself in `~/.local/share/cursor-agent/versions/<version>/.running/<pid>` with the name it was run by and the second it started, such as `cursor-agent|Sat Nov 14 21:54:52 2026`, or `agent|…` when run as `agent`. The CLI unlinks its marker when it quits. Its node worker, a child of the CLI, writes a `node|…` marker that outlives it. A marker names no chat, so a hook stays: `beforeSubmitPrompt`, registered in `~/.cursor/hooks.json`, binds the chat to the CLI's process. Of the hook's ancestors whose marker matches the second they started, that is the nearest whose parent has no such marker, so the worker is passed over whatever the processes are called. The hook also says that the turn started. A second hook, `stop`, is read for its statuses `aborted` and `error`, because some interrupts and failures leave the transcript as it was.

| What Cursor writes | Session becomes |
| --- | --- |
| `beforeSubmitPrompt`, under a marked process | working |
| A transcript ending in a user or assistant record, after the turn's end or with more user records | working |
| A transcript ending in `turn_ended` with status `success` | stopped, or question as a weak signal when the last assistant text ends in a question mark |
| `turn_ended` with status `error` | error |
| `turn_ended` with status `aborted` | idle (no light) |
| `stop` with status `aborted`, for a bound chat | idle (no light) |
| `stop` with status `error`, for a bound chat whose transcript ends in `turn_ended` with status `error` | error |
| The bound chat's `store.db-wal`, once seen, deleted, or, when the daemon starts, `store.db` there without it | removed |
| The bound process's marker unlinked, or the process gone | removed |

The transcript is not appended to only. The first checkpoint of every turn truncates the file in place and writes it again whole, without the earlier turns' `turn_ended` records. So the daemon reads the whole file each time it changes and takes a read only if it is unchanged across the read, ends in a newline, and is not the start of the read taken before. A read caught in the middle of a rewrite is the start of that earlier read, so it is skipped. Only the last record and the count of user records matter, so rewritten history changes nothing. An interrupt before the turn's first checkpoint rewrites the previous turn's `success` as `aborted`; that reads as an interrupt. When the previous turn had already ended `aborted`, the rewrite leaves the file as it was, so only the `stop` hook tells of the interrupt. A failure rewrites the transcript as it was before the turn, with `turn_ended` and status `error` after it, and a second failure like the first writes the same bytes, so only its `stop` hook, with status `error`, tells of it. Cursor runs `stop` with status `error` after every interrupt too, once the transcript ends `aborted`, so the daemon takes that status only when the transcript ends in an error. A `stop` that completes is ignored, since the transcript says the same. The prompt's hook runs before the chat's store is made, so a log not yet seen says nothing; a quit deletes the log as well as the marker. The store, its log and its `-shm` appear together at the first prompt, and a resumed chat's log appears before its prompt, so a daemon that starts to find a bound chat's `store.db` without its log does not follow the chat. Subagent transcripts, in the chat's `subagents/` folder, are never read, and a subagent, in the foreground or the background, runs no `beforeSubmitPrompt`, so it never shows as a chat of its own. The files are undocumented; the fixtures in `tests/fixtures/cursor/`, recorded from Cursor 2026.11.13, pin what the daemon expects of them.

The gaps:

- No question state. Nothing is written while a tool waits for approval, and the hooks that run before a tool fire for approved tools too, so a session waiting for approval stays green. The `AskQuestion` dialog was never offered to the model, so what it writes is unknown.
- That `stop` runs on an interrupt that writes nothing is read from Cursor's code, not from a real session.
- While Cursor retries a lost connection, the session shows working. Against a refused connection or an endpoint answering 503, `-p` retried 10 or 11 times over seven to eight minutes, then wrote `turn_ended` with status `error`, which shows as error.
- A `-p` run that fails on its first request runs neither hook, so it never shows.
- Cursor writes a reply's reasoning after its text, in the same block. With a reasoning model, the question test reads the reasoning's last line instead of the reply's, so a question can show as stopped and a statement as a question. The probe used the Auto model, which wrote no reasoning; the account's Free plan refuses every other model, so a reasoning model's transcript has not been seen.
- A chat no hook bound names no process, so it does not show. That includes every chat already running when the daemon first starts with this version: it shows from its next prompt.
- A daemon that starts in the instant between SQLite making a new chat's `store.db` and its log does not follow the chat until its next prompt.
- Work a turn leaves running, such as a background job or a background subagent, is not seen: the turn's `turn_ended` shows the session stopped until that work starts a new turn. A background subagent's transcript appears after its parent's turn has ended, and nothing names which subagent a turn started. Its completion starts that turn in the chat the process is on, which after a resume is another chat.
- A process killed with `kill -9` leaves its marker. The daemon sees that the process is gone at its next liveness check, within seconds.

## Junie

Junie keeps its folder at `$JUNIE_HOME`, or at `~/.junie` in the account's home directory, which it takes from the system and never from `$HOME`. The daemon finds it the same way, from the environment launchd starts it with, which a `JUNIE_HOME` exported in a shell's profile never reaches: set it there too with `launchctl setenv JUNIE_HOME <folder>`, then run `agent-leds install` to restart the service. `agent-leds doctor` reads the folder the service reads, says when the shell's `JUNIE_HOME` names another, and has a Junie line once the folder exists where the service or the shell finds it. Each Junie process writes a sidecar to `processes/` naming the session it takes, and each session appends its events to `sessions/<session>/events.jsonl`, which its first prompt creates. The daemon reads both as they change, and registers no hooks: an install removes the ones an older agent-leds registered in `~/.junie/config.json`, with the file their hook kept, `~/.local/state/agent-leds/junie-session.json`.

| What Junie writes | Session becomes |
| --- | --- |
| `UserPromptEvent`, or `TaskStartedEvent` when a task resumes | working |
| A block waiting in state `INPUT_REQUIRED` with an `approvalRequest` | question |
| An `AskAsyncRequestUpdatedEvent` or `ChoiceRequestUpdatedEvent` waiting in state `INPUT_REQUIRED` | question |
| The waiting step written again as `COMPLETED` or outside `INPUT_REQUIRED`, the user's response, or a `CancelAgentEvent` | working |
| `TaskState FAILED`, or `TaskState` after an `AgentFailureEvent` or `AgentTaskFailedEvent` | error |
| `TaskState` after a `CancelAgentEvent` | idle (no light) |
| `TaskState` whose result's last line ends in a question mark | question, as a weak signal |
| `TaskState` otherwise | stopped |
| A newer sidecar for the pid naming another session, the sidecar deleted, or its process gone | removed |

Junie never removes a sidecar, and one process takes session after session (the session changes once the trust screen is answered), so the sidecar with the newest `startedAt` for a pid names the session it runs, and a sidecar counts only while a process with its pid started no later than the millisecond of its `startedAt`, which may be the start itself floored to the millisecond. Junie writes one `TaskState` for each task, `COMPLETED` even after a failure, so any `TaskState` ends the task, and how it ended is read from what the task wrote before it; and it writes every block of a task again as `COMPLETED` when the task ends, which answers nothing and asks nothing. Steps are told apart by `stepId` and ordered by their place in the file, since `timestampMs` goes backwards. An events log has reached hundreds of gigabytes, as Junie writes terminal output into it, so a log is only ever read from its end, or from its start when it began after its session did. A session a process takes while the daemon runs begins idle, and only a daemon starting reads a log back to where its last task began. Of a log begun before its process took the session, as for a resume, only what that process wrote counts, from the first task it began after its `startedAt`, so a daemon started after a resume never shows the wait or the task a killed process left. Only a task start's stamp tells which process wrote a record, since a task's end writes its blocks again with their first stamps, a killed process's among them, so a seed reads back to a task start, at most 16 MiB, and a resumed task that has written more than that seeds idle. The session's folder comes from the sidecar's `projectPath`, or from a later `CurrentDirectoryUpdatedEvent` when that is empty.

The gaps:

- Junie was not installed when the files were studied. Every record is taken from captures of Junie CLI 26.8.24 that others published, and the fixtures in `tests/fixtures/junie/` are those captures with the text scrubbed, so every signal is inferred until a real session confirms it. So that a newer Junie that writes otherwise shows, a daemon starting logs, and `agent-leds doctor` reports, as for every harness, how many lines of the running sessions' logs, as far as the seed reads them back, are not records, and how many records are of kinds or wrap blocks of kinds those captures and the parsers built on them never showed.
- What a denied permission writes, whether Esc and Ctrl-C both write `CancelAgentEvent`, whether a resume appends to the same log, and what a subagent writes in `subagents/` and `task-*/` are not known. Those logs are not read.
- No hook is registered for `PermissionRequest` or `PreToolUse`, ever: Junie reads a hook that succeeds there as approving the request or allowing the tool.

## OpenCode

Every OpenCode process, the terminal interface, `opencode serve`, `opencode run`, the desktop app and 2.x's background service alike, writes its sessions to one SQLite database, `~/.local/share/opencode/opencode.db`. OpenCode 1.x writes a session to `session`, `message` and `part`, with an event log. 2.x writes it to `session_v2` and `session_message`: the session's row says when its latest run started (`time_busy`), when it went idle and how the run ended (`time_idle`, `idle_outcome`), and when the user last saw it idle (`time_viewed`), and `job` holds the shells and subagents a session left at work in the background. 2.x's first start copies 1.x's sessions into its own tables and leaves 1.x's where they are. 1.x, such as the 1.18.25 the desktop app and Zed's agent bundle, goes on writing only 1.x's tables there, and 2.x running a copied session writes only its own, so the daemon reads each session from the tables of its latest run: 2.x's once the session's row there has a run that started after 1.x's latest message.

The daemon keeps one read-only connection to the database, and opens it again when the file is replaced or its schema changes, as when 2.x first migrates it. When the database or its write-ahead log changes and `PRAGMA data_version` says another process committed, it reads, in one short transaction, where each session it follows stands: the last event of the session and of its subagents' sessions, and in 2.x the session's jobs, and, for a session where those moved, its latest messages or its row. It never reads the account or credential tables.

The database names no process and records no permission request, so the install also writes a plugin, `~/.config/opencode/plugins/agent-leds.js`, that runs `agent-leds hook opencode` for what the database leaves out. One file serves both versions: its default export holds the `server` 1.x runs and the `setup` 2.x runs. It passes on `busy`, as a session goes busy in 1.x or a run starts in 2.x, and in 2.x also at the first step or permission a process publishes for a session, since a run the service resumes as it starts again, or one under way as the plugin loads, has no start, with the pid of the process that runs the plugin, which in 2.x is the background service or the server a terminal interface or `opencode run` starts with `--standalone`; `permission.asked` and `permission.replied`; and, from 1.x, `session.error`, only while the session is busy and never for a `ContextOverflowError`, since 1.x also publishes it for a file it could not read and for an overflow it compacts, and goes on. A session is followed from its first `busy`, or a subagent's under it when it is not followed, for as long as that process runs. 2.x loads the plugin again when its file changes, so an install reaches a service that is running. 2.x goes on without a plugin it cannot load and says so only in `~/.local/share/opencode/log/opencode.log`, so `agent-leds doctor` reports such a failure when it came after the plugin was written.

| What is read | Session becomes |
| --- | --- |
| The plugin's `busy`; in 1.x a new user message as the session's latest; in 2.x a new run, as when a finished background job wakes the session | working |
| A `question` tool running in the turn (1.x) or in the latest assistant message (2.x), in the session or a subagent's | question |
| The plugin's `permission.asked`, for the session or a subagent's | question |
| The question tool done, or the plugin's `permission.replied` to the last request still waiting | working; in 2.x, working in the background again when the run had ended with a subagent's job left |
| 1.x: the latest assistant message completed, other than a step that finished on `tool-calls` or `unknown` with no error and no tool the user refused or dismissed; 2.x: the session idle since its latest run started | stopped |
| The same, its last text part ending in a question mark | question, as a weak signal |
| 2.x: the same, with a subagent's job of the session's left in `job` | working, in the background |
| 2.x: the session seen idle since it went idle, which the terminal interface writes as it shows the session with the terminal focused | read |
| 1.x: an error on that message, or the plugin's `session.error`; 2.x: the run's outcome `failed` | error |
| 1.x: a `MessageAbortedError`, or the message completed with neither finish nor error; 2.x: the run's outcome `interrupted` | idle (no light) |
| The session's row deleted or archived, or the OpenCode process gone | removed |

1.x's rule is its own: its loop goes on after a step that finished on `tool-calls` or `unknown`, however its tools fared, and writes the next step's message only after it has read the session's messages again, so such a step can be the latest message for a while. A turn the user rejected a permission in, or dismissed a question in, ends on `tool-calls` with that tool errored and nothing after it, which counts as stopped; a permission rejected with feedback lets the turn go on. 2.x says on the row when a run ends and how, so it needs no such rule. A 2.x job ends by waking its session with a new run that reports it: a shell's job is marked completed, with no event, and goes as that run starts. Only a subagent's job keeps the session working in the background: a shell may never exit, as a dev server does not, so a run that leaves one ends stopped, and its wake shows working again. 2.x writes a run's start before the plugin hears of it, so a run that failed at once, as for an unknown model, may have ended by the time its `busy` comes, and is told from the row then. A subagent runs in a session of its own whose `parent_id` names the session that started it; its questions and permissions hold that session up, and its own runs say nothing more of it. Each turn's end is told once, so the title OpenCode writes after the first turn does not announce it again. The database is undocumented; the fixtures in `tests/fixtures/opencode/`, taken from real sessions of 1.19.5, 1.18.25 and 2.3.0, pin what the daemon expects of it.

The gaps:

- A pending permission is in the database only as a running tool, in 1.x and 2.x alike, so only the plugin says it waits. A daemon that was not running when it was asked shows the session working until it moves on, one that was not running when it was replied shows it as a question until the turn ends, and one started while two requests waited takes the first reply for the answer.
- In 1.x, an error before a turn's first step, such as an unknown model, is in the database at most as a prompt with no reply. OpenCode 1.19.5 goes busy before it looks the model up, so the plugin's `session.error` shows it; 1.17.3 failed that way without ever going busy. A prompt that fails before the session goes busy, for an unknown agent or command, writes nothing and is not shown. 2.x writes such a run as `failed`.
- A turn waiting out a provider's retries shows as working, since nothing is written while it waits.
- In 1.x, a step that overflowed the context and is compacted automatically is written as a step stopped with neither finish nor error, as an abort while retrying is, and its compaction is written just after. A read between the two shows the session idle for that moment. Compaction in 2.x was not tried.
- With `experimental.continue_loop_on_deny` set, a rejected permission lets a 1.x turn go on; the session shows stopped until its next step is written.
- A session whose 1.x process started before the plugin was installed, or before an upgrade changed it, is not shown until that process is restarted.
- A 2.x run that OpenCode cuts short as it shuts down, as `opencode service stop` does, writes no end, and the job of a subagent so stopped stays in `job`. Until the service starts again the session that left the job shows working in the background, or is removed with the process that ran it. The service resumes them when it starts, each with its first step, which the plugin passes on as `busy`, so the session is followed again from where the database leaves it.
- Of 2.x's clients, only the terminal interface was seen to write that the user saw a session idle. A session no terminal interface shows idle, as one `opencode run` runs through the service, or one quit before it showed the end, is never read: its light stays until its next prompt, a dismiss or `abandon_days`, or until the process that ran it ends, which for a run through the service is the service stopping.
- A database from OpenCode before 1.18, which has no event log, is not read; the daemon says so in its log.
- Checked against OpenCode 1.19.5 through `opencode serve` and the terminal interface, with permissions, questions, aborts, a subagent, errors, an archive, a deletion and a kill, and 1.18.25 through `opencode run`. Checked against 2.3.0 through its background service, its terminal interface with and without `--standalone`, and `opencode run`, with permissions, a question, an interrupt, an unknown model, a shell moved to the background, a background subagent and its permissions, a deletion and a stopped service, and on a 1.18.25 database 2.3.0 migrated, with both running its sessions. The desktop app, 2.x's experimental `session_part` rows, which are read but were never written in the probe, and Zed's agent were not tried.

## Pi

Pi writes each session to a file, `~/.pi/agent/sessions/--<cwd>--/<time>_<session>.jsonl`, appending an entry as each message ends, and the daemon reads it as it grows. No file says which process runs a session, when an extension's dialog holds a run up, or whether an error is final, since Pi retries some, so the install also writes an extension, `~/.pi/agent/extensions/agent-leds.ts`, that passes those moments to `agent-leds hook pi`. Its `session_start` and `agent_start` name Pi's own pid and the session's file, which binds the session to its process and tells the daemon where to read, a folder set by `sessionDir` or `--session-dir` included. The extension reports only a Pi with a UI, in its terminal interface or RPC mode, as an editor integration runs it. Print and JSON modes have no one waiting on them, and pi-subagents runs its children in them, so their files, a level deeper than a cwd's folder, are never read.

| What Pi writes or the extension tells | Session becomes |
| --- | --- |
| `agent_start`, a prompt in the file, or a reply after the run ended, as when a background subagent's report wakes Pi | working |
| `ui_prompt_start` during a run: an extension's dialog holds it up | question |
| `ui_prompt_end`, or the next entry after the dialog | working |
| An assistant entry that ends the turn on a line ending in a question mark | question, as a weak signal |
| An assistant entry that ends the turn otherwise | stopped |
| `agent_settled` after an error | error |
| An assistant entry the user stopped, or `agent_settled` after a stop | idle (no light) |
| `session_shutdown` other than a reload, another session starting in the same Pi process, or the Pi process gone | removed |

An error entry in the file settles nothing, because Pi may retry it; only `agent_settled`, which comes once nothing will run by itself, says the turn failed. The extension keeps the run's abort signal from `agent_start`, so `agent_settled` says whether the user stopped the run whatever Pi wrote of it. Pi 0.84.4 writes a stop during a tool as an error with the abort's text, so for a daemon that starts after the hook, or misses it, an entry the user stopped is told by its text, never by a provider's error that only mentions an abort. 0.84.4 also writes a new session's first prompt to no file until the reply ends, so `agent_start` says the turn runs. A background subagent's report is written whether or not it wakes Pi, so only a reply after it says a run began. A fork or clone copies the turns before it into its new file, and those are never read as new; a session resumed, in a new Pi or with `/resume` in the same one, starts where its file ends.

What it cannot see:

- A dialog answered while the daemon was down still shows as a question when it starts, until the run writes its next entry, since nothing is written while a dialog is open.
- A daemon started while a session writes to its own `sessionDir` cannot find the file, so the session shows nothing until its next prompt names the file again.
- A session the Pi process left with `/new` or `/resume` while the daemon was down still shows when it starts, since that process is alive, until the new session's next prompt binds it.
- A Pi process started before the extension was installed, or before an upgrade changed it, runs the extension it loaded then, and its sessions are not shown until it is restarted or runs `/reload`.
- The hook does not wait for the daemon, which reads the file before each hook it handles. A reply written before the daemon handles that run's `agent_start` would leave the session working until its next event; no real provider answers that fast.
- On Pi 0.84.4, a stop while Pi waits to retry an error aborts no run, and nothing records it, so the session shows the error. Pi 1.5.2's `agent_settled` says it was stopped.
- A background subagent still at work when the turn ends is not seen: the session shows stopped until its report wakes Pi and a reply starts a run.
- Pi has no permission prompts of its own; extensions that add them ask through dialogs, which show as a question. A session Pi keeps no file of, as with `--no-session`, is not shown.

Checked against Pi 0.84.4 and 1.5.2 in RPC mode, with this extension installed. Pi Durable, Pi's library for long-running agent apps, is a framework rather than a harness and is not covered.
